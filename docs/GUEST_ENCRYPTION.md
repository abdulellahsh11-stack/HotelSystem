# تشفير بيانات النزلاء — دليل التفعيل

## أولاً: افهم ما تشتريه

التشفير هنا **عند التخزين** (at rest). قبل أي خطوة، افهم حدّه:

| الخطر | هل يحميه التشفير؟ |
|---|---|
| نسخة احتياطية مسروقة أو مسرَّبة | ✅ نعم |
| لقطة قاعدة بيانات تُنسَخ لجهاز مطوّر | ✅ نعم |
| مزوّد الاستضافة أو مدير قاعدة البيانات | ✅ نعم |
| موظفٌ في منشأتك يفتح النظام بحسابه | ❌ **لا** — هذا شغل الصلاحيات |
| مهاجمٌ اخترق الخادم وملك المفتاح | ❌ **لا** |

**«التشفير إلا لفلان» ليس آليةً واحدة بل اثنتان:**

```
تسريب قاعدة البيانات  →  التشفير      →  services/guest_crypto.py
مستخدم غير مخوَّل      →  الصلاحيات   →  guests.pii في المسارات
```

من ظنّهما شيئاً واحداً ظنّ نفسه محمياً وهو ليس كذلك.

## من يرى بيانات النزيل كاملة؟

| الدور | الهوية والجوال | السبب |
|---|---|---|
| مالك المنشأة | ✅ | صاحب البيانات |
| مدير عام | ✅ | يدير كل التشغيل |
| مدير مناوبة | ✅ | يُتمّ تسجيل الوصول |
| موظف استقبال | ✅ | لا تسجيل وصول بلا هوية |
| إشراف داخلي | ❌ مُقنَّع | التنظيف لا يحتاج هوية |
| محاسب | ❌ مُقنَّع | الفاتورة تُصدَر برقم الحجز |
| كاشير | ❌ مُقنَّع | نقطة البيع لا تحتاج هوية |

المُقنَّع يعرض `••••••5432` — يكفي لتمييز نزيلٍ عن آخر ولا يكشف الرقم.

> **شموس:** التصدير الحكومي يقرأ عبر طبقة التخزين، فيحصل على القيم
> الصريحة بعد الفكّ. لا يمرّ بالتقنيع لأنه ليس عرضاً لمستخدم.

## ما الذي يُشفَّر؟

| الحقل | مشفَّر؟ | السبب |
|---|---|---|
| `id_number` | ✅ | أخطر حقل — رقم الهوية أو الجواز |
| `absher_phone` | ✅ | يُعرِّف الشخص خارج المنصة |
| `birth_date` | ✅ | مع الاسم يكفي لانتحال الهوية |
| `notes` | ✅ | يحوي ملاحظات صحية أحياناً |
| `full_name` | ❌ **بالصلاحيات لا بالتشفير** | يُبحَث به ويُعرَض في كل قائمة؛ تشفيره يعني فكّ كل صفٍّ عند كل بحث — أي تعطيل البحث. والاسم وحده، بلا هوية ولا جوال ولا ميلاد، قيمتُه لسارق القاعدة ضئيلة |

## خطوات التفعيل

### ١ — ولّد مفتاحين منفصلين

```bash
python3 -c "from services.guest_crypto import generate_key; print(generate_key())"  # GUEST_ENCRYPTION_KEY
python3 -c "from services.guest_crypto import generate_key; print(generate_key())"  # GUEST_INDEX_KEY
```

> منفصلان عمداً: تسريب أحدهما لا يُسقط الآخر.

### ٢ — احفظ نسخةً من المفتاحين **خارج المنصة**

خزانة كلمات مرور، أو ورقة في خزنة. **لا باب خلفياً**: ضياع المفتاح
يعني أن أرقام الهوية لا تعود أبداً.

### ٣ — خذ نسخة احتياطية

```bash
pg_dump "$DATABASE_URL" > backup_before_encryption.sql
```

هذه ليست توصية.

### ٤ — اضبط المتغيّرين في Railway وأعد النشر

الترحيل يوسّع الأعمدة تلقائياً عند الإقلاع (`db/schema_guest_crypto.py`).

### ٥ — شفّر الصفوف القائمة

```bash
python3 scripts/encrypt_existing_guests.py --dry-run   # إحصاء بلا كتابة
python3 scripts/encrypt_existing_guests.py --apply     # التنفيذ
```

قابلٌ لإعادة التشغيل: الصفّ المشفَّر يُتخطّى.

### ٦ — تأكّد

سجّل نزيلاً، ثم اقرأ الصفّ من قاعدة البيانات مباشرةً:

```sql
SELECT id_number FROM guests ORDER BY id DESC LIMIT 1;
-- يجب أن ترى: v1:xxxx:yyyy   لا رقم هوية
```

ثم ادخل بحساب «إشراف داخلي» وتأكّد أن الهوية تظهر مُقنَّعة.

## البحث بعد التشفير

النصّ المشفَّر لا يُبحَث فيه: نفس الرقم يُنتج نصّاً مختلفاً كل مرة —
وهذا **مقصود**، فالتشفير الحتمي يكشف من تكرّر رقمُه دون فكّ.

فيُخزَّن مع الرقم **فهرسٌ أعمى**: `HMAC-SHA256` بمفتاح منفصل. يُطابَق
ولا يُعكَس، والبحث يُرسل البصمة لا الرقم — فحتى سجلّ الاستعلامات
البطيئة لا يحوي أرقام هوية.

## تدوير المفتاح

الصيغة تبدأ بـ`v1:` لهذا الغرض. التدوير يحتاج سكربتاً يقرأ بالمفتاح
القديم ويكتب بالجديد — **لم يُكتب بعد**. اكتبه قبل أن تحتاجه، لا بعد.

---

## ما لم يُنجَز بعد

- تدوير المفاتيح (الصيغة تدعمه، السكربت غير مكتوب)
- تشفير الاسم (قرارٌ مؤجَّل — انظر الجدول أعلاه)
- خدمة إدارة مفاتيح حقيقية (KMS) بدل متغيّر بيئة
- سجلّ تدقيق لمن كشف بيانات أي نزيل ومتى
