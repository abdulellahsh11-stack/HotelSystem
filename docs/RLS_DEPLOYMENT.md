# تفعيل عزل قاعدة البيانات (RLS)

طبقة الدفاع الثانية للعزل بين المنشآت. الأولى شرط `client_id` في كل
استعلام؛ هذه تجعل **قاعدة البيانات نفسها** ترفض، فنسيانُ الشرط يصير
خطأً في النتيجة لا تسريباً صامتاً.

الشيفرة جاهزة ومُثبَتة على PostgreSQL حقيقي. التفعيل قرارٌ تشغيلي
يتطلّب الخطوات الثلاث **بهذا الترتيب**.

---

## ترتيب الخطوات — عكسُه يوقف المنصة

### ١ — تطبيق السياسات (بمستخدم يملك الجداول)

```bash
RLS_APPLY_ON_STARTUP=1  # مرة واحدة، ثم أزِله
```

يُنفَّذ لكل جدول:

- `ENABLE ROW LEVEL SECURITY`
- **`FORCE ROW LEVEL SECURITY`** — بدونها يتجاوز مالكُ الجدول السياسة،
  والتطبيق يُنشئ الجداول فهو مالكها. هذه الكلمة وحدها هي الفرق بين
  حماية حقيقية وحمايةٍ تبدو مُفعَّلة وهي صفر.
- سياسة `USING` + `WITH CHECK`
- فهرس على `client_id`

### ٢ — تحويل الاتصال إلى دور تطبيق لا يتجاوز RLS

```sql
CREATE ROLE dheuof_app LOGIN PASSWORD '<من متغيّر بيئة>'
    NOSUPERUSER NOCREATEDB NOBYPASSRLS;
```

ثم جمل المنح في `db.rls.app_role_sql()`، وتحديث `DATABASE_URL`.

> **الـsuperuser يتجاوز RLS دائماً — حتى مع `FORCE`.** قِسنا ذلك
> مباشرةً. فهذه الخطوة ليست تحسيناً بل شرط عمل الحماية أصلاً.
> `postgres` أو أي دور `SUPERUSER` يُلغي كل ما سبق.

### ٣ — تشغيل المفتاح

```bash
RLS_ENABLED=1
```

عندها تضبط طبقةُ الاتصال سياقَ المستأجر داخل معاملة كل استعلام.

---

## كيف تعمل السلسلة

```
طلب HTTP
   ↓  bind_tenant_context (middleware)   ← الجلسة، لا مُدخل المستخدم
ContextVar
   ↓  _bind_tenant_context (db/connection)
SELECT set_config('app.current_client_id', …, true)   ← داخل نفس المعاملة
   ↓
سياسة RLS ← الصفوف المُعادة
```

**لماذا داخل نفس المعاملة:** السياق محليٌّ للمعاملة، وكل `execute()`
معاملةٌ مستقلة. ضبطه في نداء منفصل يضيع قبل أن يصل الاستعلام — قِسنا
ذلك على خادم حقيقي، وهو ما كان يمنع التفعيل قبل هذه الهيكلة.

**ولماذا محلياً لا على مستوى الجلسة:** الاتصالات مُجمَّعة ويُعاد
استعمالها. سياقٌ يبقى بعد المعاملة يُورَّث لطلب منشأة أخرى — تسريبٌ
يظهر تحت الحِمل وحده فيصعب تشخيصه.

---

## مالك المنصة

يعبر المنشآت عبر `platform_scope()` وحده، ويُفتح في مسارات المشرف بعد
`require_admin` ولأضيق كتلة ممكنة. متغيّرٌ منفصل (`app.platform_admin`)
لا قيمةٌ خاصة في متغيّر المستأجر — فلا يُبلغ بتمرير معرّف.

جدول `clients` خارج RLS: هو سجلّ المنشآت نفسه، ومنه تُبنى لوحة المشرف.

---

## التراجع

```bash
RLS_ENABLED=0   # يُعيد الاعتماد على الطبقة الأولى فوراً
```

السياسات تبقى في قاعدة البيانات بلا أثر، لأن تجاوزها يعتمد على دور
الاتصال. للتراجع الكامل: أعِد `DATABASE_URL` إلى مستخدم مالك الجداول.

---

## التحقق بعد التفعيل

```bash
TEST_DATABASE_URL="<اتصال إداري>" pytest tests/test_rls_isolation.py tests/test_rls_end_to_end.py -q
```

يفحصان: العزل، ورفض التعديل والحذف عبر المنشآت، و`WITH CHECK`، والفشل
المغلق بلا سياق، وعدم تسرّب السياق بين الطلبات، ونطاق مالك المنصة.

أولُ اختبار في `test_rls_isolation.py` يتحقق أن دور الاختبار **لا
يتجاوز RLS** — لأن تشغيلها بدورٍ مالك يجعلها تمرّ بلا أن تفحص شيئاً،
وهو بالضبط ما جعل RLS في هذا المستودع صفراً عملياً قبل هذا العمل.

---

## الأداء

كل استعلام صار يحمل `set_config` إضافية — رحلة ذهاب وإياب واحدة على
نفس الاتصال. الفهارس على `client_id` مُطبَّقة ضمن الخطوة ١ وهي شرط لا
رفاهية: بدونها يفحص المُخطِّط الجدول كاملاً في كل استعلام.

قِس قبل التفعيل وبعده على بيانات حقيقية. إن استُعمل PgBouncer، فوضع
`transaction` آمنٌ مع هذا التصميم لأن السياق محليٌّ للمعاملة.
